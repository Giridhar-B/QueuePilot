# QueuePilot – REST API Design

## 1. API Overview

QueuePilot exposes REST APIs that allow client applications to submit, manage, schedule, and monitor background jobs.

### API conventions

| Property | Convention |
|---|---|
| Base URL | `/api/v1` |
| Data format | JSON |
| Authentication | API key |
| Authentication header | `X-API-Key` |
| Identifier format | UUID |
| Timestamp format | ISO 8601 (UTC) |
| Pagination | Page number and page size |
| API versioning | URL-based versioning |

All endpoints except public health and readiness endpoints require authentication.

## 2. Authentication

Clients authenticate using an API key.

Request header:

    X-API-Key: qp_live_your_api_key

API keys are generated by QueuePilot and associated with an account.

The backend validates the supplied key by securely comparing its hash with the stored hash.

Raw API keys are never stored in PostgreSQL.

## 3. Job Management APIs

### 3.1 Submit a Job

**POST** `/api/v1/jobs`

Submits a new background job.

Example request:

    {
      "type": "EMAIL",
      "payload": {
        "to": "user@example.com",
        "subject": "Welcome",
        "body": "Welcome to QueuePilot!"
      },
      "priority": "HIGH",
      "maxAttempts": 3,
      "timeoutSeconds": 60,
      "availableAt": null
    }

Example response: `202 Accepted`

    {
      "id": "job-uuid",
      "type": "EMAIL",
      "status": "QUEUED",
      "priority": "HIGH",
      "attemptCount": 0,
      "maxAttempts": 3,
      "createdAt": "2026-11-04T10:00:00Z"
    }

Supports an optional `Idempotency-Key` request header to prevent duplicate job creation when clients retry submissions.

### 3.2 Get Job Details

**GET** `/api/v1/jobs/{jobId}`

Returns details about a specific job owned by the authenticated account.

### 3.3 List Jobs

**GET** `/api/v1/jobs`

Supports filtering and pagination.

Query parameters:

- `status` – Filter by job status.
- `type` – Filter by job type.
- `priority` – Filter by priority.
- `page` – Page number.
- `size` – Number of records per page.
- `sort` – Sorting field and direction.

Example:

    GET /api/v1/jobs?status=FAILED&page=0&size=20

### 3.4 Cancel a Job

**POST** `/api/v1/jobs/{jobId}/cancel`

Requests cancellation of an eligible job.

Initially, cancellation is supported for QUEUED and RETRY_WAIT jobs. Running jobs will not be forcefully terminated through this endpoint.

### 3.5 Retry a Failed Job

**POST** `/api/v1/jobs/{jobId}/retry`

Requests a manual retry of an eligible FAILED job.

The system records the retry and returns the job to the execution pipeline.

### 3.6 Get Job Attempts

**GET** `/api/v1/jobs/{jobId}/attempts`

Returns the execution history, including attempt number, worker ID, execution duration, status, and failure information.

## 4. Scheduling APIs

### 4.1 Create a Schedule

**POST** `/api/v1/schedules`

Creates a one-time or recurring job schedule.

Example request:

    {
      "name": "Daily Report",
      "type": "PDF",
      "scheduleType": "RECURRING",
      "cronExpression": "0 0 9 * * *",
      "timezone": "Asia/Kolkata",
      "payload": {
        "reportType": "DAILY"
      }
    }

### 4.2 Get Schedule Details

**GET** `/api/v1/schedules/{scheduleId}`

### 4.3 List Schedules

**GET** `/api/v1/schedules`

Supports pagination and filtering by schedule status and type.

### 4.4 Update a Schedule

**PUT** `/api/v1/schedules/{scheduleId}`

Updates an existing schedule.

### 4.5 Pause a Schedule

**POST** `/api/v1/schedules/{scheduleId}/pause`

### 4.6 Resume a Schedule

**POST** `/api/v1/schedules/{scheduleId}/resume`

### 4.7 Delete a Schedule

**DELETE** `/api/v1/schedules/{scheduleId}`

Deletes or deactivates an eligible schedule. Previously generated jobs remain available.

## 5. Dashboard APIs

### 5.1 Get Job Statistics

**GET** `/api/v1/dashboard/statistics`

Returns account-level statistics:

- Total jobs
- Queued jobs
- Running jobs
- Successful jobs
- Failed jobs
- Jobs waiting for retry

### 5.2 Get Recent Jobs

**GET** `/api/v1/dashboard/recent-jobs`

Returns recently submitted and executed jobs.

### 5.3 Get Queue Statistics

**GET** `/api/v1/dashboard/queue-statistics`

Returns queue and worker metrics, such as pending jobs, active executions, and processing counts.

These statistics are account-scoped where appropriate. Infrastructure-wide metrics must not expose other accounts' job information.

## 6. Health and Monitoring APIs

These endpoints are intended for operational monitoring rather than normal client job management.

### 6.1 Application Health

**GET** `/actuator/health`

Returns application health.

### 6.2 Application Metrics

**GET** `/actuator/metrics`

Exposes configured application metrics.

Actuator access will be restricted appropriately and must not expose sensitive operational information publicly.

## 7. Standard API Responses

### Successful response

    {
      "id": "job-uuid",
      "status": "QUEUED"
    }

### Error response

    {
      "timestamp": "2026-11-04T10:00:00Z",
      "status": 400,
      "error": "Bad Request",
      "code": "VALIDATION_ERROR",
      "message": "Invalid job payload",
      "path": "/api/v1/jobs"
    }

### Common HTTP status codes

| Status | Meaning |
|---|---|
| 200 | Successful request |
| 201 | Resource created |
| 202 | Request accepted for asynchronous processing |
| 204 | Successful request with no response body |
| 400 | Invalid request |
| 401 | Missing or invalid API key |
| 403 | Authenticated but not permitted |
| 404 | Resource not found or not accessible |
| 409 | Resource conflict |
| 429 | Rate limit exceeded |
| 500 | Internal server error |
| 503 | Service temporarily unavailable |

## 8. Security and Validation

All authenticated job and schedule operations must enforce account ownership.

Security requirements:

- API key authentication.
- Hashed API key storage.
- Account-level resource isolation.
- Request validation.
- Payload size limits.
- Rate limiting.
- Protection against unauthorized job access.
- Safe error responses without exposing internal stack traces or secrets.

## 9. API Design Principles

1. Use RESTful resource-oriented endpoints.
2. Version the API through its URL.
3. Use consistent request and response formats.
4. Validate requests before processing.
5. Enforce account ownership on every resource operation.
6. Return appropriate HTTP status codes.
7. Support pagination for collection endpoints.
8. Document endpoints using OpenAPI.
9. Keep job submission asynchronous.
10. Never expose internal implementation details or sensitive credentials in API responses.

## 10. Implementation Notes

This document defines the initial API contract.

Exact response DTOs, validation rules, pagination metadata, rate limits, and error codes will be finalized during implementation.

The dashboard will use the same authenticated API rather than accessing the database directly.
